# shared/

## ConnectKit

A local Swift Package (`ConnectKit/`) with three targets:

- **`MessagingCoreFFI`** — a `.binaryTarget` pointing at
  `MessagingCoreFFI.xcframework`. Not committed to git (see below) —
  generated by `build-core-apple.sh`.
- **`MessagingCore`** — the Swift bindings [UniFFI](https://mozilla.github.io/uniffi-rs/)
  generates from `core/`'s Rust API (a `ConnectClient` object, a
  `ConnectClientListener` callback interface, `ChatMessage` and
  `ConnectionState` types). Also not committed — generated alongside the
  XCFramework, into `ConnectKit/Sources/MessagingCore`.
- **`ConnectKit`** — the actual app: SwiftUI views (`ContentView`,
  `Theme`) plus `NetworkClient`, a thin wrapper that implements
  `ConnectClientListener` and republishes its callbacks as `@Published`
  properties for SwiftUI to observe. This is committed normally; it's
  hand-written source, not generated.
- **`FFISmokeTest`** — a CLI executable target for exercising
  `MessagingCore.ConnectClient` directly, no UI involved. See the root
  [README](../README.md#testing-the-rust-swift-ffi-directly).

## Why the FFI bindings aren't committed

`MessagingCoreFFI.xcframework` and `Sources/MessagingCore` are both
regenerated from `core/`'s Rust source by `build-core-apple.sh` — they're
build output, not something to hand-edit or review as source. Same
reasoning as not committing `target/`: keeping them out of git means
there's exactly one source of truth (the Rust code) instead of two things
that can drift out of sync.

This means **`swift build`/`swift run`/`xcodebuild` in `macos/` or `ios/`
will fail with "target not found" until you've run the build script at
least once.**

## `build-core-apple.sh`

Run this after any change under `core/src/`, before building either app:

```bash
./shared/build-core-apple.sh
```

What it does:

1. `cargo build -p messaging-core --release` for both
   `aarch64-apple-darwin` (macOS) and `aarch64-apple-ios-sim` (iOS
   Simulator) — real iOS *device* support isn't set up yet, only
   Simulator.
2. Runs `uniffi-bindgen` (a small `[[bin]]` target inside `core/`, see
   `core/uniffi-bindgen.rs`) in **library mode** — it inspects the built
   `.dylib` directly rather than needing a separate `.udl` interface
   file, since `core/src/client.rs` declares everything with proc macros
   (`#[derive(uniffi::Object)]`, `#[uniffi::export]`, etc.). Outputs
   `messaging_core.swift` plus a C header/modulemap.
3. Combines both platform `.dylib`s + the shared header into one
   `MessagingCoreFFI.xcframework` via `xcodebuild -create-xcframework`.

## A gotcha worth knowing: absolute build paths

Both `swift build` (macOS) and `xcodebuild` (iOS) link the resulting
executable against the `.dylib` by its **absolute path** in `target/`
(e.g. `/Users/you/Connect/target/aarch64-apple-darwin/release/deps/...`),
not a portable `@rpath`-relative one. That's fine for `swift
run`/`xcodebuild build` themselves — the absolute path is still valid,
since nothing moved. It breaks the moment you copy just the executable
into an app bundle for distribution (`macos/Connect.app`,
`ios/Connect.app`): the copied binary would still be pointing at the
original machine's build directory.

`macos/build-app.sh` and `ios/build-app.sh` both handle this: they copy
the `.dylib` into the bundle and use `install_name_tool` to rewrite both
the dylib's own install name and the executable's reference to it, so the
bundle finds its own embedded copy via `@executable_path` instead. Don't
hand-copy just the executable when making a distributable bundle — use
the scripts, or replicate what they do.

## Adding a real iOS device target later

Not done yet (deliberately deferred). Would need:
`rustup target add aarch64-apple-ios`, a build for that target in
`build-core-apple.sh`, and a third `-library`/`-headers` pair in the
`xcodebuild -create-xcframework` call. Real devices also can't use an
ad-hoc `codesign --sign -` the way the Simulator can — `ios/build-app.sh`
would need a real signing identity/provisioning profile to install on
physical hardware.
